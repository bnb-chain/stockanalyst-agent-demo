# Binance B402 V2 Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the obsolete Binance Pay HMAC settlement path with a fail-closed Binance B402 V2 integration and make the asynchronous buyer submit the official V2 payment payload.

**Architecture:** A new Python `B402Client` owns merchant configuration, exact-body RSA signing, `/supported` caching, `/verify`, and `/settle`. The existing x402 handler injects the discovered EIP-3009 kind into paid challenges and delegates settlement to the client, while the existing job service keeps its idempotency boundary. The TypeScript buyer obtains the 402 requirement before signing and submits the official V2 payload.

**Tech Stack:** Python 3.10+, `httpx`, `pycryptodome`, `unittest`; TypeScript, Node test runner, `ethers`.

## Global Constraints

- Support only B402 V2 EIP-3009 `exact` payments on BSC Testnet (`eip155:97`) in this change.
- Read `B402_CLIENT_ID`, `B402_ACCESS_TOKEN`, `B402_BASE_URL`, and `B402_PRIVATE_KEY` from the environment; never log their values.
- `B402_BASE_URL` has no guessed or production default.
- Sign the exact transmitted UTF-8 JSON body plus the exact millisecond timestamp using RSA PKCS#1 v1.5 SHA-256.
- Fetch `/supported`, cache it for one hour, and copy the complete matching `extra` mapping into every paid 402 challenge.
- Call `/verify` successfully before `/settle`; never run report work before confirmed settlement.
- Do not create, inspect, deploy, or send the user's credentials.
- Do not invoke a real B402 settlement as part of tests.
- Preserve the existing generic facilitator, explicit demo mode, free endpoint, S3 job idempotency, and report-delivery behavior.
